# Prototyping

## 目的

実際の利用感と実装上の成立性を同じコードで確かめ、未確定の仕様・設計を本実装で再現できる決定へ変える。

## 成果

反復中は常に次の二つを揃える。

1. 現在採用している決定を実現し、関係する検証を通した動作可能な実装
2. 現在の決定、重要な代替案、検証結果、未決事項を区別した設計記録

実装を観測して、次を満たすことを確認する。

- 本番で提供・保守できる品質である。
- ユーザーが別方式を明示しない限り、既存コードへ本実装と同じ形で統合されている。
- 設計記録の現在の決定と一致する。
- 変更に関係する検証結果が最新である。

設計記録を観測して、次を満たすことを確認する。

- ユーザーが別の配置を指定しない限り、`docs/design/YYMMDD_*.md` に置く。`YYMMDD` はセッション開始日とする。
- 記録を作成または更新する前に `assets/design-record-template.md` を最後まで読み、セッション中は一つの記録を正確な見出しのまま更新する。
- 「現在の決定」には、ユーザーとの反復で明示的に固定した採用中の事項だけがある。
- 外部から観測できる挙動を仕様、実現する内部構造を設計として分離する。
- 重要な代替案は、対応する現在の決定と棄却根拠を参照できる。
- 実装、決定、検証、未決事項、Status が互いに矛盾しない。
- Status は `Proposed`、`Accepted`、`Deprecated`、`Superseded by [<新しい設計記録>](<相対パス>)` のいずれかである。
- Status の遷移は `Proposed` から `Accepted`、`Accepted` から `Deprecated`、または `Accepted` から `Superseded by [...]` だけである。
- `Accepted` 後は本文を変更しない。決定を置き換える場合は新しい設計記録を作り、旧記録では Status だけを `Superseded by [...]` に変える。置き換える決定なしに廃止する場合だけ `Deprecated` に変える。

## 反復

実装変更、関連する検証、設計記録の更新を同じ反復内で行い、成果の不変条件を回復する。便宜的に実装しただけの詳細を決定へ昇格させない。ユーザーが終了を明示するまで Status を `Proposed` に保ち、反復可能な状態を維持する。終了時は未決事項が最終成果へ混入していないことを確認し、Status を `Accepted` にする。

## 圧力下でも守る境界

| 誘惑 | 必須の扱い |
|---|---|
| 「試作だから `scratch/` と fake state でよい」 | 本実装と同じ統合経路と現実的な状態で判断する。 |
| 「選定後に捨てて作り直す」 | 採用案をそのまま本実装へ進められる品質にする。 |
| 「デモだけなので手動確認でよい」 | 変更に関係する再実行可能な検証を残す。 |
| 「履歴のため旧案も現在の決定に残す」 | 現在の決定には採用案だけを置き、旧案は代替案として対応付ける。 |

これらが現れたら、時間制約を理由に成果の定義を変えず、対象範囲を縮める。
