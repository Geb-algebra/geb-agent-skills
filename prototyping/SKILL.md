# Prototyping

## 目的

実際の利用感と実装上の成立性を同じコードで確かめ、未確定の仕様・設計を本実装で再現できる決定へ変える。実装を捨ててやり直す場合も、確定済みの知見を失わずに再実装できる状態を保つ。

## 成果

反復中の成果は常に次の二つが揃った状態である。

1. 現在採用している決定を実現し、関係する検証を通した動作可能な実装である。
2. 現在の決定、重要な代替案、検証結果、未決事項を区別した設計記録である。

実装は次の状態である。

- 本番で提供・保守できる品質である。
- ユーザーが別方式を明示しない限り、既存コードへ本実装と同じ形で統合されている。
- 設計記録の現在の決定と一致している。
- 変更に関係する検証結果が最新である。

設計記録は次の状態である。

- 設計記録は、prototyping 開始時の current branch をベースブランチとして、その通常の作業ツリーで更新されている。
- ユーザーが別の配置を指定しない限り、`docs/design/YYMMDD_*.md` に置かれている。`YYMMDD` はセッション開始日である。
- 作成または更新の前に `assets/design-record-template.md` が最後まで読まれており、セッション中の記録は一つで、見出しがテンプレートと正確に一致している。
- 「現在の決定」には、ユーザーとの反復で明示的に固定した採用中の事項だけがある。
- 実装用 worktree とそのブランチがどの時点で失われても、現在の実装に含まれる重要な決定事項を再現できるだけの明示的な記述がベースブランチ上にある。
- 現在採用している重要な決定事項のうち、実装用 worktree、そのブランチ、または未 commit の変更にしか存在しないものはない。
- 外部から観測できる挙動は仕様、実現する内部構造は設計として分離されている。
- 重要な代替案は、対応する現在の決定と棄却根拠を参照できる。
- 実装、決定、検証、未決事項、Status が互いに矛盾しない。
- Status は `Proposed`、`Accepted`、`Deprecated`、`Superseded by [<新しい設計記録>](<相対パス>)` のいずれかである。
- Status の遷移は `Proposed` から `Accepted`、`Accepted` から `Deprecated`、または `Accepted` から `Superseded by [...]` だけである。
- `Accepted` 後の本文は変更されていない。決定を置き換えた場合は新しい設計記録が存在し、旧記録では Status だけが `Superseded by [...]` である。置き換える決定なしに廃止した場合だけ Status が `Deprecated` である。

実装環境は次の状態である。

- 実装は、prototyping 開始時にベースブランチから作成した専用ブランチの worktree 内だけで行われている。
- ユーザーが別の配置を指定しない限り、worktree はリポジトリルート直下の `.worktrees/` 内にある。
- `.worktrees/` を既定の配置に使う場合、このディレクトリはリポジトリの `.gitignore` の無視対象である。
- ベースブランチ上の各設計記録更新に対応する commit が存在し、その commit はベースブランチから worktree 側のブランチへ merge 済みで、実装側の設計記録と同期している。
- 設計記録の編集はベースブランチ側、実装とその検証の変更は worktree 側に分離されている。

## 開始

開始時の current branch をベースブランチとして固定する。実装を変更する前に、そのベースブランチから専用ブランチと worktree を作成する。既定ではリポジトリルートの `.worktrees/` を作成先とし、必要なら `.gitignore` に追加する。以後、設計記録はベースブランチの通常の作業ツリー、実装と検証は専用 worktree で扱う。

## 反復

worktree 内の実装変更と関連する検証、ベースブランチ側の設計記録の更新を同じ反復内で行い、成果の不変条件を回復する。設計記録を更新したらベースブランチで commit し、そのベースブランチを worktree 側のブランチへ merge してから反復を続ける。便宜的に実装しただけの詳細を決定へ昇格させない。ユーザーが終了を明示するまで Status を `Proposed` に保ち、反復可能な状態を維持する。終了時は未決事項が最終成果へ混入していないことを確認し、Status を `Accepted` にする。

## 圧力下でも守る境界

| 誘惑 | 必須の扱い |
|---|---|
| 「試作だから `scratch/` と fake state でよい」 | 本実装と同じ統合経路と現実的な状態で判断する。 |
| 「選定後に捨てて作り直す」 | 採用案をそのまま本実装へ進められる品質にする。 |
| 「デモだけなので手動確認でよい」 | 変更に関係する再実行可能な検証を残す。 |
| 「履歴のため旧案も現在の決定に残す」 | 現在の決定には採用案だけを置き、旧案は代替案として対応付ける。 |
| 「小さな変更なので設計記録も worktree 側で直す」 | 設計記録はベースブランチ側だけで更新し、commit 後にベースブランチを worktree 側へ merge する。 |
| 「動いてからまとめて設計記録へ書けばよい」 | worktree をその時点で捨てても重要な決定を再現できる粒度で、ベースブランチの設計記録を反復中も最新に保つ。 |

これらが現れたら、時間制約を理由に成果の定義を変えず、対象範囲を縮める。
